# Cleanup-truck integration

## Intended outcome

The software provides the perception, operator-assistance, counting, and local
evidence layer for a larger cleanup or refuse-collection system. It can:

- detect and classify visible litter from a truck-mounted camera;
- track objects so the same item is not counted in every frame;
- show a worker the suggested material separation stream;
- send uncertain classifications to a human review queue;
- preserve observations locally while the truck has no network connection;
- expose durable events to fleet software;
- record a separate confirmation when a human or collection controller reports
  that an item was actually picked up.

The detector is not a motion controller and does not establish that an object
was collected.

## Operational flow

```text
camera or stream
      |
      v
public/custom litter detection and classification
      |
      v
tracking, counting, and separation policy
      |
      +---------------------> operator display
      |                       class / confidence / destination / REVIEW
      |
      +---------------------> SQLite observation store
      |                       runs / frame counts / reviews / outbox
      |
      +---------------------> candidate-object integration event
                              |
                              v
                     task or arm planner
                              |
                              v
               safety-rated controller and interlocks
                              |
                              v
                  external pickup confirmation
                              |
                              v
                     SQLite and fleet event
```

## One-command truck run

```bash
./startup.sh \
  --source 0 \
  --edge-device-id edge-truck-01 \
  --vehicle-id truck-12 \
  --route-id route-a \
  --no-display
```

The defaults write:

- frame evidence to `reports/generated/`;
- persistent operational state to `state/litter-edge.db`;
- confirmed-object and run-completion messages to the SQLite integration
  outbox.

Use a supervisor such as systemd or the truck platform's process manager for
automatic restart after power or camera interruption.

## Human-assisted separation

`config/separation.yaml` maps each litter class to an operator-defined workflow
destination. The display includes that destination in the box label.

Low-confidence detections, hazardous categories, and `other_litter` are marked
`REVIEW` and written to the review queue. A local interface can retrieve the
queue:

```http
GET /v1/review-queue?status=pending
```

It can then confirm, correct, or reject an item:

```http
POST /v1/review-queue/{review_id}
Content-Type: application/json

{
  "status": "corrected",
  "corrected_class_name": "metal_can",
  "corrected_destination": "metal_stream",
  "reviewed_by": "operator-1"
}
```

Separation mappings are site policy, not universal recycling claims. The
operator remains responsible for hazardous, mixed, contaminated, or ambiguous
material.

## SQLite operational model

SQLite runs in write-ahead-log mode for local durability and concurrent
readers. The schema contains:

| Table | Purpose |
|---|---|
| `runs` | Session, device, vehicle, route, source, status, and performance |
| `frame_observations` | Per-frame visible and unique count snapshots |
| `detections` | Optional detailed boxes when `--persist-detections` is enabled |
| `run_class_counts` | Query-friendly final counts by class |
| `review_queue` | Human confirmations, corrections, and rejections |
| `collection_confirmations` | Externally confirmed physical pickups |
| `integration_outbox` | Durable messages awaiting fleet-system acknowledgement |

Frame and run records are automatic. Detailed detection rows are opt-in to
limit disk growth.

The operator should set a retention and backup policy appropriate to shift
length, frame rate, available storage, and privacy requirements. Monitor the
database and its `-wal` file; use SQLite's online backup mechanism instead of
copying a live database file without coordination.

## Observed versus collected

These quantities must remain separate:

1. `visible_counts`: objects visible in one frame;
2. `unique_session_counts`: confirmed track IDs observed during one run;
3. `confirmed_collected_counts`: pickups explicitly confirmed by a human,
   arm controller, sensor-fusion component, or reviewed import.

Collection confirmation is submitted through:

```http
POST /v1/collections
Content-Type: application/json

{
  "run_id": "RUN_ID",
  "track_id": 7,
  "class_name": "plastic_bottle",
  "quantity": 1,
  "method": "arm_controller",
  "external_reference": "controller-pickup-0001"
}
```

The `external_reference` should be an idempotency identifier generated by the
external controller. Duplicate references and duplicate track confirmations
are rejected.

## Fleet integration

Start the local read/review/integration API without loading the model:

```bash
./startup.sh --counts-api
```

Useful interfaces:

```http
GET  /v1/counts/summary
GET  /v1/runs
GET  /v1/review-queue
POST /v1/review-queue/{review_id}
GET  /v1/integration/events
POST /v1/integration/events/{event_id}/ack
POST /v1/collections
```

The outbox pattern supports intermittent connectivity:

1. the edge process commits an operational record and integration event in the
   local database;
2. a fleet connector reads pending events;
3. the connector sends them using the operator's authenticated transport;
4. only after the remote platform accepts an event does the connector
   acknowledge it locally.

The repository provides the local durable boundary. Cloud credentials,
transport selection, fleet tenancy, and remote retention belong to the
integrating organization.

## Mechanical safety boundary

Model output is advisory perception data. It must not directly command
hydraulic, pneumatic, or electric movement.

A production arm integration requires, independently of this repository:

- a safety-rated controller with final actuation authority;
- emergency-stop and manual-override circuits;
- human and obstacle exclusion-zone sensing;
- arm-position, load, and reach limits;
- fail-safe behavior for stale, missing, or contradictory sensor data;
- positive pickup confirmation from the controller or sensor fusion;
- hazard handling for batteries, chemicals, sharps, pressurized containers,
  and unknown objects;
- a documented functional-safety assessment for the vehicle and jurisdiction.

If any safety input is unavailable or disagrees with perception, the arm should
remain inhibited and the item should be routed to human review.

## Operational measures

The useful system-level outcomes are:

- litter objects observed by class and route;
- reviewed/corrected classification rate;
- detected-to-confirmed-collection conversion;
- uncollected or repeatedly observed hotspots;
- false pickup proposals and missed pickup opportunities;
- database/outbox backlog during network loss;
- inference availability during a shift.

Accuracy is evaluated for the frozen release-model configuration used by the
solution. The product evaluation focuses on whether the complete workflow helps
collection teams find, separate, and account for litter safely; it does not
rank detector families.
